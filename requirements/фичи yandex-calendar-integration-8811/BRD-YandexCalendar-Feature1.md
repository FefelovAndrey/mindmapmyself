# BRD — Интеграция узла с Яндекс Календарём (Фича #1)

**Ветка (документы):** `docs/yandex-calendar-tz`  
**Версия:** 1.1  
**Дата:** 21.08.2026  
**Статус:** ТЗ уточнено после приёмки v1.0 (неверный тип объекта в Календаре)  
**Связанные документы:**
- `Plans/yandex-calendar-api.md` — CalDAV / OAuth
- `requirements/BRD.md` — модель узла v1.x
- `types/node.ts` — текущая схема

---

## 1. Цель

Дать возможность из карточки узла (правая панель) создать в Яндекс Календаре **событие с типом «Задача»** (не отдельную задачу VTODO и не встречу), видеть признак привязки и одной кнопкой подтянуть из календаря актуальные дату/время и факт выполнения.

**Как в UI Яндекс Календаря:** диалог «Новое событие» → вкладка **«Задача»** (рядом с «Встреча») → календарь **«Мои события»**.

**Не цель (v1):**
- создание **VTODO** в списке задач (`todos-*`);
- создание **встречи** (вкладка «Встреча» / VEVENT без типа «Задача»);
- двусторонняя синхронизация названия/описания;
- контекстные меню на outline/карте;
- multi-user / чужие календари.

---

## 2. Как есть (контекст)

| Аспект | Сейчас |
|--------|--------|
| Карточка узла | `NodeCard` справа: имя, ответственный, статус, срок (`deadline` = только дата), описание |
| Время суток у узла | **нет** |
| Сохранение карты | автосохранение + кнопка «Сохранить» (снимок) и индикатор статуса в шапке |
| Календарь | CalDAV `caldav.yandex.ru`, OAuth (`calendar:all`), секреты в `.env.local` |
| Календарь событий | `events-35737546` («Мои события») — **целевая коллекция для v1** |
| Список задач (`todos-*`) | **не** использовать для этой фичи |

---

## 3. Функциональные требования

### FR-1. Отправка узла в Календарь как события типа «Задача»

**Где:** только в правой панели (`NodeCard`) для выбранного узла.

**UI в карточке:**
- выбор **даты**;
- выбор **временного диапазона** (время начала и время окончания);
- кнопка **«Отправить в календарь»** (или эквивалент).

**Что создаётся в Яндекс Календаре:**
- объект типа **событие** с подтипом / режимом **«Задача»** (как на вкладке «Задача» в диалоге «Новое событие»);
- **не** запись в списке задач (VTODO / `todos-*`);
- **не** встреча (вкладка «Встреча»).

**Маппинг в событие Календаря (VEVENT + тип «Задача»):**

| Поле события | Источник |
|--------------|----------|
| Название (`SUMMARY`) | `node.name` |
| Описание (`DESCRIPTION`) | `node.description` (если `null` — пустое / без поля) |
| Начало (`DTSTART`) | выбранные дата + время начала |
| Окончание (`DTEND`) | выбранные дата + время окончания |
| Тип | **Задача** (не встреча) — см. FR-6, точный iCalendar-маркер уточняется при реализации |
| Коллекция CalDAV | календарь событий (`YANDEX_EVENTS_CALENDAR_ID`, по умолчанию `events-35737546` / «Мои события») |

**После успешного создания:**
- узел связывается с событием (сохраняется внешний идентификатор CalDAV `UID` и при необходимости путь);
- в карточке отображается **признак**, что узел создан в календаре (см. FR-2);
- в модели узла сохраняются дата/время начала и окончания, переданные при создании (см. FR-5).

**Ограничения v1:**
- связь **1 узел ↔ 0..1 событие типа «Задача»**;
- повторная отправка уже привязанного узла — **запрещена** (кнопка неактивна / сообщение «Уже в календаре»);
- ошибки сети/CalDAV показываются пользователю, узел не помечается привязанным.

**Критерий визуальной приёмки:** в веб-UI Яндекс Календаря созданная запись открывается/отображается как **событие с типом «Задача»** в календаре «Мои события», а не как элемент списка задач и не как встреча.

---

### FR-2. Признак «создан в календаре»

- В `NodeCard` у привязанного узла виден явный признак (бейдж / иконка / текст вроде «В календаре»).
- Признак опирается на наличие связи в данных узла (не на «угадывание» по названию).
- В outline/карте в v1 **не обязательно** дублировать признак (допустимо только в карточке).

---

### FR-3. Синхронизация узлов ↔ календарь (одна кнопка)

**Где:** в шапке приложения рядом с индикатором сохранения / кнопкой «Сохранить».

**Кнопка:** «Синхронизировать с календарём» (название может уточняться в UI).

**Область:** все узлы дерева, у которых есть привязка к календарю.

**Для каждого привязанного узла при успехе:**

1. **Дата и время** из события календаря обновляют поля даты/времени узла (начало и окончание диапазона: `DTSTART` / `DTEND`).
2. Если событие типа «Задача» в календаре отмечено как **выполненное**:
   - `status` узла → `Done`;
   - в `description` **добавляется** (не затирает существующий текст) строка:

   ```
   Выполнена в календаре дд.мм.гггг чч:мм
   ```

   где `дд.мм.гггг чч:мм` — момент выполнения в календаре (если доступен в iCalendar).  
   Если момента выполнения **нет** — подставляются дата и время **момента этой синхронизации** (локальный TZ приложения).

**Правила текста в описании:**
- дописывать в конец, с переносом строки при необходимости;
- если такая же пометка уже есть — **не дублировать** (идемпотентность по префиксу `Выполнена в календаре`);
- учитывать лимит описания **2000** символов: если не влезает — не дописывать молча; показать предупреждение / зафиксировать ошибку по узлу в результате sync (см. AC).

**Направление v1:** только **календарь → приложение** (дата/время, Done + пометка).  
Изменения имени/описания/статуса в приложении **не** пушатся обратно в календарь в рамках этой фичи.

---

### FR-4. Поведение статуса

| Ситуация | Поведение v1 |
|----------|--------------|
| Событие-задача в календаре выполнено | узел → `Done` + пометка в описании |
| Событие снова не выполнено | **не** откатывать `Done` автоматически (v1) |
| Пользователь вручную меняет статус в NodeCard | разрешено; при следующей sync снова может стать `Done`, если в календаре выполнено |
| Событие удалено в календаре | sync: снять привязку **или** показать ошибку по узлу; дату/статус не затирать молча — см. OQ-3 |

**Решение по умолчанию (OQ-3):** если событие не найдено (404) — снять признак привязки и `calendarUid`, оставить локальные дату/время/статус/описание как есть, в итоге sync показать предупреждение «событие не найдено в календаре».

### FR-5. Модель данных (расширение `MindNode`)

Добавить поля (имена можно слегка изменить при реализации, смысл зафиксирован):

| Поле | Тип | Смысл |
|------|-----|--------|
| `calendarUid` | `string \| null` | UID **события** в CalDAV; `null` = не привязан |
| `calendarStartAt` | `string \| null` | начало диапазона, ISO 8601 с оффсетом или UTC |
| `calendarEndAt` | `string \| null` | конец диапазона, ISO 8601 |
| `calendarSyncedAt` | `string \| null` | время последней успешной sync по узлу |

**Связь с существующим `deadline`:**
- `deadline` (дата `YYYY-MM-DD`) **сохраняется** для узлов без календаря и как раньше редактируется в карточке;
- после привязки к календарю:
  - источником истины для планирования становятся `calendarStartAt` / `calendarEndAt`;
  - при создании и при sync: `deadline` = **дата** из `calendarStartAt` (календарный день начала), чтобы outline/фильтры по сроку не ломались;
  - редактирование `deadline` вручную у **привязанного** узла в v1 — **заблокировано** (read-only / скрыто), чтобы не было двух конфликтующих дат.

**Время в UI привязанного узла:** в `NodeCard` показывать начало и конец из `calendarStartAt` / `calendarEndAt` (не только дату).

### FR-6. Техническая интеграция

- Протокол: **CalDAV**.
- Компонент iCalendar: **`VEVENT`** (событие), **не `VTODO`**.
- Семантика UI Яндекса: событие с типом **«Задача»** (вкладка «Задача» в «Новое событие»), календарь **«Мои события»**.
- Коллекция: `YANDEX_EVENTS_CALENDAR_ID` (например `events-35737546`), **не** `YANDEX_TODOS_CALENDAR_ID`.
- Аутентификация: OAuth-токен из env (`.env.local`: `YANDEX_OAUTH_TOKEN`, `YANDEX_CALENDAR_EMAIL`, `YANDEX_EVENTS_CALENDAR_ID`).
- Серверные route handlers (предложение):
  - `POST /api/calendar/events` — создать событие типа «Задача» из узла;
  - `POST /api/calendar/sync` — синхронизация всех привязанных узлов.
- После create/sync клиент обновляет дерево и сохраняет через существующий `POST /api/nodes`.
- Часовой пояс v1: **`Asia/Yekaterinburg`** (UTC+5), согласованно с UI календаря на стенде.

**Маркер типа «Задача» в iCalendar (обязательно уточнить до реализации):**
- при реализации экспериментально определить, каким свойством Яндекс отличает вкладку «Задача» от «Встреча» (например `X-…`, `CATEGORIES` и т.п.);
- без этого маркера приёмка **не** считается пройденной, даже если VEVENT появился в `events-*`.

---

## 4. Нефункциональные требования

- Секреты не в `mindmap.json` и не в git.
- Офлайн: без сети create/sync недоступны; остальной редактор работает как раньше.
- Sync при большом числе привязок: последовательные или умеренно параллельные запросы; итог с числом успехов/ошибок.
- Не ломать существующие карты: новые поля опциональны (`null` / отсутствие = нет календаря).

## 7. Критерии приёмки (Acceptance Criteria)

### AC-1. Отправка в календарь

| ID | Given / When / Then |
|----|---------------------|
| AC-1.1 | **Given** выбран узел без `calendarUid`, **When** пользователь указывает дату, время начала и окончания и нажимает «Отправить в календарь», **Then** в Яндекс Календаре в **«Мои события»** появляется **событие с типом «Задача»** (не элемент списка задач, не встреча) с `SUMMARY` = имя узла и описанием из узла (или пусто). |
| AC-1.2 | **Given** успешный ответ CalDAV, **When** операция завершена, **Then** у узла заполнены `calendarUid`, `calendarStartAt`, `calendarEndAt`, `deadline` = дата начала, и в карточке виден признак «В календаре». |
| AC-1.3 | **Given** узел уже с `calendarUid`, **When** пользователь смотрит карточку, **Then** отправка недоступна без создания дубликата. |
| AC-1.4 | **Given** конец диапазона раньше начала (или равен началу), **When** отправка, **Then** запрос не уходит, показывается ошибка валидации. |
| AC-1.5 | **Given** CalDAV вернул ошибку / нет сети, **When** отправка, **Then** узел остаётся без привязки, признак не показывается, пользователь видит сообщение об ошибке. |
| AC-1.6 | **Given** успешная отправка, **When** пользователь открывает созданную запись в UI Яндекс Календаря, **Then** видит объект как событие вкладки/типа **«Задача»** в календаре событий (см. эталонный UI). |

### AC-2. Признак привязки

| ID | Given / When / Then |
|----|---------------------|
| AC-2.1 | **Given** узел с `calendarUid`, **When** открыта карточка, **Then** признак «в календаре» отображается. |
| AC-2.2 | **Given** узел без `calendarUid`, **When** открыта карточка, **Then** признака нет. |

### AC-3. Глобальная синхронизация

| ID | Given / When / Then |
|----|---------------------|
| AC-3.1 | **Given** в шапке есть кнопка sync, **When** на карте есть ≥1 привязанный узел и пользователь нажимает sync, **Then** приложение запрашивает актуальные данные **событий** из CalDAV (коллекция `events-*`). |
| AC-3.2 | **Given** в календаре у события изменены дата/время, **When** sync успешен, **Then** у соответствующего узла обновлены `calendarStartAt` / `calendarEndAt` и `deadline` (дата начала). |
| AC-3.3 | **Given** событие-задача в календаре отмечено выполненным и известно время завершения, **When** sync, **Then** `status` узла = `Done` и в конец `description` добавлена строка `Выполнена в календаре дд.мм.гггг чч:мм`. |
| AC-3.4 | **Given** событие выполнено, но времени завершения нет, **When** sync, **Then** в пометке используется дата/время момента sync. |
| AC-3.5 | **Given** в описании уже есть строка, начинающаяся с `Выполнена в календаре`, **When** повторный sync, **Then** вторая такая же пометка не добавляется. |
| AC-3.6 | **Given** существующее описание узла непустое, **When** добавляется пометка о выполнении, **Then** исходный текст описания сохраняется. |
| AC-3.7 | **Given** добавление пометки превысило бы 2000 символов, **When** sync, **Then** основной текст не затирается; пометка не добавляется «тихо»; по узлу — ошибка/предупреждение. |
| AC-3.8 | **Given** нет привязанных узлов, **When** sync, **Then** no-op без ошибки. |
| AC-3.9 | **Given** частичный успех sync, **When** завершён, **Then** успешные узлы обновлены, по неуспешным видно ошибку. |

### AC-4. Данные и сохранение

| ID | Given / When / Then |
|----|---------------------|
| AC-4.1 | **Given** create или sync изменили узлы, **When** операция успешна, **Then** изменения сохраняются через существующий механизм (`POST /api/nodes` / снимок). |
| AC-4.2 | **Given** карта без календарных полей (старый JSON), **When** загрузка, **Then** узлы работают как раньше. |
| AC-4.3 | **Given** секреты CalDAV, **When** проверка репозитория, **Then** токен/пароль не в git. |

### AC-5. UI / UX минимальный

| ID | Given / When / Then |
|----|---------------------|
| AC-5.1 | **Given** выбран узел, **When** правая панель, **Then** доступны контролы даты, диапазона времени и отправки (если не привязан). |
| AC-5.2 | **Given** узел привязан, **When** карточка, **Then** видны дата/время начала и окончания из календарных полей. |
| AC-5.3 | **Given** любая вкладка (Outline/Карта), **When** шапка, **Then** кнопка sync доступна рядом с сохранением. |

## 8. Вне скоупа v1

- Создание **VTODO** / работа со списком задач `todos-*`  
- Создание **встреч** (вкладка «Встреча») и Телемост  
- Push изменений имени/описания/статуса из приложения в календарь  
- Кнопки create/sync на outline и на карте  
- Несколько событий на один узел  
- Выбор чужого календаря / нескольких аккаунтов  
- Авто-sync по таймеру / webhook

## 9. Проверочный сценарий (smoke)

1. Открыть узел без календаря → указать завтра 09:00–10:00 → Отправить.  
2. В [calendar.360.yandex.ru](https://calendar.360.yandex.ru/) в **«Мои события»** появилась запись как **событие типа «Задача»** с именем узла; в карточке — признак.  
3. Убедиться, что запись **не** в списке задач и **не** оформлена как встреча.  
4. В календаре перенести событие на другой день/время → Sync в шапке → на узле новые дата/время.  
5. Отметить событие-задачу выполненной в календаре → Sync → статус Done + строка в описании.  
6. Sync ещё раз → вторая строка «Выполнена…» не появляется.
