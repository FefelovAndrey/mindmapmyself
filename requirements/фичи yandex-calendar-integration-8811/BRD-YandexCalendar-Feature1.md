## 1. Цель

Из карточки узла создать в Яндекс Календаре **встречу** (`VEVENT` / вкладка «Встреча» в «Мои события»), видеть признак привязки, подтягивать **только дату и время** из календаря в узел, а при переводе узла в `Done` — один раз пометить название встречи префиксом `(Done)` и **прекратить** дальнейшую синхронизацию по этому узлу.

**Не цель (v1):**
- создание UI-типа «Задача» (вкладка «Задача» — **не видна через CalDAV**, см. эксперимент);
- создание **VTODO** / список «Не забыть» (`todos-*`);
- перенос статуса «выполнено» **из календаря на узел** (у встречи нет статуса «Выполнен»);
- двусторонняя синхронизация описания;
- постоянная синхронизация названия;
- контекстные меню на outline/карте; multi-user / чужие календари.

## 3. Функциональные требования

### FR-1. Отправка узла в Календарь как **встречи**

**Где:** только в правой панели (`NodeCard`) для выбранного узла.

**UI в карточке:**
- выбор **даты**;
- выбор **временного диапазона** (начало и окончание);
- кнопка **«Отправить в календарь»**.

**Что создаётся:** обычная **встреча** в «Мои события» (CalDAV: `VEVENT` в `events-*`).  
В веб-UI Яндекса запись открывается как событие вкладки **«Встреча»**.

**Маппинг:**

| Поле встречи | Источник |
|--------------|----------|
| `SUMMARY` | `node.name` |
| `DESCRIPTION` | `node.description` (если `null` — пусто / без поля) |
| `DTSTART` / `DTEND` | выбранные дата + время начала / окончания |
| Коллекция | `YANDEX_EVENTS_CALENDAR_ID` (по умолчанию `events-35737546`) |

**После успеха:**
- сохраняются `calendarUid` (и при необходимости путь), `calendarStartAt`, `calendarEndAt`;
- `deadline` = дата из `calendarStartAt`;
- в карточке — признак «В календаре» (FR-2);
- `calendarSyncStopped` = `false` (sync даты/времени разрешён).

**Ограничения v1:**
- связь **1 узел ↔ 0..1 встреча**;
- повторная отправка при наличии `calendarUid` — **запрещена**;
- конец диапазона **строго позже** начала (нулевая длительность запрещена);
- ошибки сети/CalDAV — без привязки узла, сообщение пользователю.

---

### FR-2. Признак «создан в календаре»

- В `NodeCard` у привязанного узла — явный признак (бейдж / текст «В календаре»).
- Опирается на наличие `calendarUid`, не на угадывание по имени.
- На outline/карте в v1 дублировать **не обязательно**.

---

### FR-3. Синхронизация **только даты и времени** (календарь → узел)

**Где:** шапка, рядом с индикатором / «Сохранить».  
**Кнопка:** «Синхронизировать с календарём».

**Область:** узлы с `calendarUid` **и** `calendarSyncStopped !== true`  
(после пометки `(Done)` в календаре — см. FR-4 — узел в sync **не участвует**).

**Для каждого такого узла при успехе:**
1. Прочитать встречу из CalDAV.
2. Обновить у узла `calendarStartAt` / `calendarEndAt` из `DTSTART` / `DTEND`.
3. Обновить `deadline` = дата из `calendarStartAt`.
4. Обновить `calendarSyncedAt`.

**Не делать при sync:**
- менять `status` узла;
- менять `name` / `description` узла;
- писать в календарь (кроме сценария FR-4, который срабатывает не из кнопки sync, а при смене статуса).

**Если встреча не найдена (404):** снять `calendarUid` и признак привязки; локальные дата/время/статус/описание **не** затирать; предупреждение в итоге sync.

---

### FR-4. Статус узла `Done` → префикс `(Done)` в названии встречи

**Триггер:** у узла с `calendarUid` и `calendarSyncStopped !== true` статус становится **`Done`**  
(выбор в NodeCard или любой другой путь обновления статуса в приложении).

**Действие (один раз):**
1. Прочитать текущую встречу из CalDAV (нужен актуальный `SUMMARY`, если его правили вручную — по возможности сохранить хвост; см. правило ниже).
2. Установить `SUMMARY` встречи:
   - если текущий `SUMMARY` уже начинается с `(Done)` (с пробелом или без — нормализовать) — **не** дублировать префикс;
   - иначе: **`SUMMARY` = `(Done) ` + `node.name`**  
     (имя **узла** на момент проставления `Done`; название в календаре и имя узла с этого момента могут различаться — это ожидаемо).
3. `PUT` обновлённой встречи (сохранить `DTSTART`/`DTEND`/прочие поля без намеренного изменения расписания).
4. Выставить у узла **`calendarSyncStopped = true`** (и при желании `calendarSyncedAt` = сейчас).
5. Сохранить дерево через существующий механизм (`POST /api/nodes`).

**После этого по узлу:**
- кнопка глобального sync **пропускает** узел;
- повторная отправка в календарь по-прежнему запрещена;
- смена статуса с `Done` на другой **не** обязана снимать `(Done)` с календаря и **не** обязана снова включать sync (v1: sync остаётся выключенным).

**Ошибки CalDAV при пометке Done:** показать пользователю; `calendarSyncStopped` **не** ставить в `true`, чтобы можно было повторить; статус узла `Done` при этом уже может быть сохранён локально (не откатывать молча) — см. OQ-8.

### FR-5. Модель данных (расширение `MindNode`)

| Поле | Тип | Смысл |
|------|-----|--------|
| `calendarUid` | `string \| null` | UID встречи в CalDAV; `null` = не привязан |
| `calendarStartAt` | `string \| null` | начало, ISO 8601 |
| `calendarEndAt` | `string \| null` | конец, ISO 8601 |
| `calendarSyncedAt` | `string \| null` | время последней успешной операции с календарём по узлу |
| `calendarSyncStopped` | `boolean` | `true` = синхронизация даты/времени **отключена** (после пометки `(Done)` в календаре) |

**`deadline`:**
- без календаря — как сейчас;
- при создании и при sync даты: `deadline` = дата из `calendarStartAt`;
- у привязанного узла с активным sync (`calendarSyncStopped === false`) ручной `deadline` в v1 — **read-only / скрыт**;
- при `calendarSyncStopped === true` — допустимо снова разрешить ручной `deadline` (источник истины уже не календарь) — **да** (OQ-9 закрыт так).

**UI привязанного узла:** показывать начало/конец из `calendarStartAt` / `calendarEndAt`.

---

### FR-6. Техническая интеграция

- Протокол: **CalDAV**.
- Компонент: **`VEVENT`** (встреча), коллекция **`events-*`**.
- Env: `YANDEX_OAUTH_TOKEN`, `YANDEX_CALENDAR_EMAIL`, `YANDEX_EVENTS_CALENDAR_ID`.
- Routes (предложение):
  - `POST /api/calendar/events` — создать встречу из узла;
  - `POST /api/calendar/sync` — sync даты/времени по привязанным узлам с `calendarSyncStopped !== true`;
  - обновление `SUMMARY` при Done — из API смены статуса узла / отдельный вызов после `updateNode` (деталь реализации).
- TZ v1: **`Asia/Yekaterinburg`** (UTC+5).

## 4. Нефункциональные требования

- Секреты не в git / не в `mindmap.json`.
- Без сети create/sync/пометка Done в календаре недоступны; редактор работает.
- Sync: итог с числом успехов/пропусков (в т.ч. пропуск из‑за `calendarSyncStopped`) / ошибок.
- Старые карты без новых полей загружаются без падения (`null` / отсутствие = нет календаря; отсутствие `calendarSyncStopped` = `false`).

## 5. История решений (кратко)

| Версия | Суть |
|--------|------|
| v1.0 | VTODO в `todos-*` — отклонено при приёмке |
| v1.1 | Событие UI «Задача» — **невозможно через CalDAV** (эксперимент OQ-6) |
| **v1.2** | **Встреча** + sync **только** даты/времени; при `Done` узла — `(Done)` в `SUMMARY` встречи и стоп sync |

| # | Решение v1.2 |
|---|----------------|
| 1 | Объект в календаре = **встреча** (`VEVENT`) |
| 2 | Из календаря на узел тянем **только** `DTSTART`/`DTEND` (и производный `deadline`) |

| 4 | При `status → Done` в приложении: один раз `SUMMARY = "(Done) " + node.name`, затем `calendarSyncStopped = true` |
| 5 | Имя узла после этого **не** обязано совпадать с названием встречи |

## 7. Критерии приёмки (Acceptance Criteria)

### AC-1. Создание встречи

| ID | Given / When / Then |
|----|---------------------|
| AC-1.1 | **Given** узел без `calendarUid`, **When** указаны дата и диапазон времени и нажато «Отправить в календарь», **Then** в «Мои события» появляется **встреча** с `SUMMARY` = имя узла. |
| AC-1.2 | **Given** успех CalDAV, **When** операция завершена, **Then** заполнены `calendarUid`, `calendarStartAt`, `calendarEndAt`, `deadline`, `calendarSyncStopped = false`, виден признак «В календаре». |
| AC-1.3 | **Given** уже есть `calendarUid`, **When** карточка, **Then** повторная отправка недоступна. |
| AC-1.4 | **Given** конец ≤ начала, **When** отправка, **Then** валидация, запрос не уходит. |
| AC-1.5 | **Given** ошибка сети/CalDAV, **When** отправка, **Then** без привязки, с сообщением об ошибке. |
| AC-1.6 | **Given** успех, **When** открыть запись в UI Яндекса, **Then** это **встреча** (не вкладка «Задача», не элемент «Не забыть»). |

### AC-2. Признак привязки

| ID | Given / When / Then |
|----|---------------------|
| AC-2.1 | Узел с `calendarUid` → признак виден в карточке. |
| AC-2.2 | Узел без `calendarUid` → признака нет. |

### AC-3. Sync даты/времени

| ID | Given / When / Then |
|----|---------------------|
| AC-3.1 | Есть ≥1 узел с привязкой и `calendarSyncStopped !== true`, **When** Sync, **Then** читаются встречи из `events-*`. |
| AC-3.2 | В календаре сдвинули дату/время встречи, **When** Sync, **Then** у узла обновлены `calendarStartAt`/`calendarEndAt`/`deadline`. |
| AC-3.3 | **Given** sync, **Then** `status` и `description` узла **не** меняются из‑за календаря. |
| AC-3.4 | Узел с `calendarSyncStopped = true`, **When** Sync, **Then** узел **пропущен** (дата/время не обновляются из календаря). |
| AC-3.5 | Нет подходящих узлов, **When** Sync, **Then** no-op без ошибки. |
| AC-3.6 | Частичный успех → успешные обновлены, по ошибкам видно сообщение. |
| AC-3.7 | Встреча 404 → снять привязку, локальные поля не затирать, предупреждение. |

### AC-4. Done → `(Done)` в календаре

| ID | Given / When / Then |
|----|---------------------|
| AC-4.1 | **Given** узел с `calendarUid` и активным sync, **When** статус → `Done`, **Then** в CalDAV `SUMMARY` становится `(Done) ` + имя узла (на момент операции). |
| AC-4.2 | **Given** успех пометки, **When** операция завершена, **Then** `calendarSyncStopped = true`. |
| AC-4.3 | **Given** `calendarSyncStopped = true`, **When** снова Sync, **Then** этот узел не синхронизируется. |
| AC-4.4 | **Given** `SUMMARY` уже с префиксом `(Done)`, **When** повторная попытка пометки, **Then** префикс не дублируется. |
| AC-4.5 | **Given** ошибка CalDAV при пометке, **When** статус уже `Done`, **Then** пользователю ошибка; `calendarSyncStopped` остаётся `false` до успеха. |
| AC-4.6 | **Given** после пометки, **When** сравнить имя узла и `SUMMARY` встречи, **Then** они могут отличаться — это норма. |

### AC-5. Данные и сохранение

| ID | Given / When / Then |
|----|---------------------|
| AC-5.1 | Create / sync / Done-пометка → изменения узла сохраняются штатно. |
| AC-5.2 | Старый JSON без календарных полей → загрузка без падения. |
| AC-5.3 | Секреты не в git. |

### AC-6. UI

| ID | Given / When / Then |
|----|---------------------|
| AC-6.1 | Непривязанный узел → дата, время, «Отправить в календарь». |
| AC-6.2 | Привязанный узел → видны дата/время из календарных полей; признак привязки. |
| AC-6.3 | В шапке на Outline/Карте → кнопка Sync рядом с сохранением. |

## 8. Вне скоупа v1

- UI-тип «Задача» / любой объект, не отдаваемый CalDAV  
- VTODO / «Не забыть»  
- Перенос «выполнено» из календаря на узел  
- Снятие `(Done)` с календаря при смене статуса с Done  
- Телемост / участники / повтор  
- Create/sync на outline и карте  
- Несколько встреч на один узел  
- Авто-sync по таймеру

## 9. Проверочный сценарий (smoke)

1. Узел без календаря → завтра 09:00–10:00 → Отправить → в «Мои события» **встреча** с именем узла; признак в карточке.  
2. В календаре сдвинуть встречу → Sync → на узле новые дата/время; статус узла **не** меняется.  
3. Поставить узлу статус **Done** → в календаре название вида `(Done) …`; у узла sync остановлен.  
4. Снова сдвинуть встречу в календаре → Sync → **дата/время узла не меняются**.  
5. Имя узла можно переименовать — с встречей больше не сходится, и это ок.
