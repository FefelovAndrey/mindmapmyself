# BRD — Интеграция узла с Яндекс Календарём (Фича #1)

**Ветка:** `cursor/yandex-calendar-integration-8811`  
**Версия:** 1.0  
**Дата:** 21.08.2026  
**Статус:** зафиксировано по сырым требованиям заказчика (структурировано, с решениями по несоответствиям)  
**Связанные документы:**
- `Plans/yandex-calendar-api.md` — CalDAV / OAuth
- `requirements/BRD.md` — модель узла v1.x
- `types/node.ts` — текущая схема

---

## 1. Цель

Дать возможность из карточки узла (правая панель) создать **задачу** в Яндекс Календаре, видеть признак привязки и одной кнопкой подтянуть из календаря актуальные дату/время и факт выполнения.

**Не цель (v1):** двусторонняя синхронизация названия/описания; создание встреч (VEVENT); контекстные меню на outline/карте; multi-user / чужие календари.

---

## 2. Как есть (контекст)

| Аспект | Сейчас |
|--------|--------|
| Карточка узла | `NodeCard` справа: имя, ответственный, статус, срок (`deadline` = только дата), описание |
| Время суток у узла | **нет** |
| Сохранение карты | автосохранение; в шапке индикатор «Сохраняется… / Сохранено», **отдельной кнопки «Сохранить» нет** |
| Календарь | CalDAV `caldav.yandex.ru`, OAuth (`calendar:all`), секреты в `.env.local` |
| Список задач пользователя | `todos-7647328` («Не забыть») — целевая коллекция для v1 |
| Календарь событий | `events-35737546` — **не** использовать для этой фичи |

---

## 3. Функциональные требования

### FR-1. Отправка узла в Календарь как задачи

**Где:** только в правой панели (`NodeCard`) для выбранного узла.

**UI в карточке:**
- выбор **даты**;
- выбор **временного диапазона** (время начала и время окончания);
- кнопка **«Отправить в календарь»** (или эквивалент).

**Маппинг в задачу Календаря (VTODO):**

| Поле задачи | Источник |
|-------------|----------|
| Название (`SUMMARY`) | `node.name` |
| Описание (`DESCRIPTION`) | `node.description` (если `null` — пустое / без поля) |
| Начало | выбранные дата + время начала |
| Окончание / срок | выбранные дата + время окончания |
| Коллекция CalDAV | список задач (`YANDEX_TODOS_CALENDAR_ID`, по умолчанию `todos-7647328`) |

**После успешного создания:**
- узел связывается с задачей (сохраняется внешний идентификатор CalDAV `UID` и при необходимости путь);
- в карточке отображается **признак**, что узел создан в календаре (см. FR-2);
- в модели узла сохраняются дата/время начала и окончания, переданные при создании (см. FR-5).

**Ограничения v1:**
- связь **1 узел ↔ 0..1 задача**;
- повторная отправка уже привязанного узла — **запрещена** (кнопка неактивна / сообщение «Уже в календаре»);
- ошибки сети/CalDAV показываются пользователю, узел не помечается привязанным.

---

### FR-2. Признак «создан в календаре»

- В `NodeCard` у привязанного узла виден явный признак (бейдж / иконка / текст вроде «В календаре»).
- Признак опирается на наличие связи в данных узла (не на «угадывание» по названию).
- В outline/карте в v1 **не обязательно** дублировать признак (допустимо только в карточке).

---

### FR-3. Синхронизация узлов ↔ календарь (одна кнопка)

**Где:** в шапке приложения **рядом с индикатором сохранения** (это и есть место «рядом с кнопкой сохранить» в текущем UI).

**Кнопка:** «Синхронизировать с календарём» (название может уточняться в UI).

**Область:** все узлы дерева, у которых есть привязка к календарю.

**Для каждого привязанного узла при успехе:**

1. **Дата и время** из задачи календаря обновляют поля даты/времени узла (начало и окончание диапазона).
2. Если задача в календаре в статусе **выполненной**:
   - `status` узла → `Done`;
   - в `description` **добавляется** (не затирает существующий текст) строка:

   ```
   Выполнена в календаре дд.мм.гггг чч:мм
   ```

   где `дд.мм.гггг чч:мм` — момент выполнения задачи в календаре (`COMPLETED` в iCalendar).  
   Если момента выполнения в календаре **нет** — подставляются дата и время **момента этой синхронизации** (локальный TZ приложения).

**Правила текста в описании:**
- дописывать в конец, с переносом строки при необходимости;
- если такая же пометка уже есть — **не дублировать** (идемпотентность по префиксу `Выполнена в календаре`);
- учитывать лимит описания **2000** символов: если не влезает — обрезать **добавляемый** хвост нельзя молча: показать предупреждение / не дописывать и зафиксировать ошибку по узлу в результате sync (см. AC).

**Направление v1:** только **календарь → приложение** (дата/время, Done + пометка).  
Изменения имени/описания/статуса в приложении **не** пушатся обратно в календарь в рамках этой фичи.

---

### FR-4. Поведение статуса

| Ситуация | Поведение v1 |
|----------|--------------|
| Задача в календаре `COMPLETED` | узел → `Done` + пометка в описании |
| Задача снова не выполнена | **не** откатывать `Done` автоматически (v1) |
| Пользователь вручную меняет статус в NodeCard | разрешено; при следующей sync снова может стать `Done`, если в календаре выполнено |
| Задача удалена в календаре | sync: снять привязку **или** показать ошибку по узлу; дату/статус не затирать молча — см. открытый пункт OQ-3 (принято по умолчанию ниже) |

**Решение по умолчанию (OQ-3):** если задача не найдена (404) — снять признак привязки и `calendarUid`, оставить локальные дату/время/статус/описание как есть, в итоге sync показать предупреждение «задача не найдена в календаре».

---

### FR-5. Модель данных (расширение `MindNode`)

Добавить поля (имена можно слегка изменить при реализации, смысл зафиксирован):

| Поле | Тип | Смысл |
|------|-----|--------|
| `calendarUid` | `string \| null` | UID задачи в CalDAV; `null` = не привязан |
| `calendarStartAt` | `string \| null` | начало диапазона, ISO 8601 с оффсетом или UTC |
| `calendarEndAt` | `string \| null` | конец диапазона, ISO 8601 |
| `calendarSyncedAt` | `string \| null` | время последней успешной sync по узлу |

**Связь с существующим `deadline`:**
- `deadline` (дата `YYYY-MM-DD`) **сохраняется** для узлов без календаря и как раньше редактируется в карточке;
- после привязки к календарю:
  - источником истины для планирования становятся `calendarStartAt` / `calendarEndAt`;
  - при создании и при sync: `deadline` = **дата** из `calendarStartAt` (календарный день начала), чтобы outline/фильтры по сроку не ломались;
  - редактирование `deadline` вручную у **привязанного** узла в v1 — **заблокировано** (read-only / скрыто), чтобы не было двух конфликтующих дат.

**Время в UI привязанного узла:** в `NodeCard` показывать начало и конец из `calendarStartAt` / `calendarEndAt` (не только дату).

---

### FR-6. Техническая интеграция

- Протокол: **CalDAV**, компонент **VTODO** (не VEVENT).
- Аутентификация: OAuth-токен из env (`.env.local`: `YANDEX_OAUTH_TOKEN`, `YANDEX_CALENDAR_EMAIL`, `YANDEX_TODOS_CALENDAR_ID`).
- Серверные route handlers (предложение):
  - `POST /api/calendar/tasks` — создать задачу из узла;
  - `POST /api/calendar/sync` — синхронизация всех привязанных узлов.
- После create/sync клиент обновляет дерево и сохраняет через существующий `POST /api/nodes`.
- Часовой пояс v1: **`Asia/Yekaterinburg`** (UTC+5), согласованно с проверкой CalDAV на стенде.

---

## 4. Нефункциональные требования

- Секреты не в `mindmap.json` и не в git.
- Офлайн: без сети create/sync недоступны; остальной редактор работает как раньше.
- Sync при большом числе привязок: последовательные или умеренно параллельные запросы; итог с числом успехов/ошибок.
- Не ломать существующие карты: новые поля опциональны (`null` / отсутствие = нет календаря).

## 5. Несоответствия в сырых требованиях и принятые решения

| # | Несоответствие / пробел | Решение v1 |
|---|-------------------------|------------|
| 1 | В узле нет времени, только `deadline` (дата) | Добавлены `calendarStartAt` / `calendarEndAt`; `deadline` синхронизируется датой начала |
| 2 | «Кнопка сохранить» отсутствует | Sync-кнопка рядом с индикатором автосохранения в header |
| 3 | «Задача» vs встреча | Только **VTODO** в `todos-*` |
| 4 | Диапазон времени у задачи | В CalDAV: `DTSTART` = начало, `DUE` = конец диапазона |
| 5 | Откуда брать время «выполнена», если нет | Момент текущей синхронизации |
| 6 | Лимит описания 2000 | Не затирать; при переполнении — ошибка по узлу, без молчаливой обрезки основного текста |
| 7 | Повторная отправка | Запрещена при наличии `calendarUid` |
| 8 | Обратный sync статуса/текста в календарь | Нет в v1 |
| 9 | Признак на карте/outline | Только NodeCard в v1 |

## 6. Открытые вопросы (не блокируют старт UI, уточнить при реализации)

| ID | Вопрос | Временное допущение |
|----|--------|---------------------|
| OQ-1 | Нужен ли выбор «весь день» без времени? | Нет в v1 — время обязательно |
| OQ-2 | Нужна ли sync одного узла из карточки (не только глобальная)? | Только глобальная кнопка в header |

## 7. Критерии приёмки (Acceptance Criteria)

### AC-1. Отправка в календарь

| ID | Given / When / Then |
|----|---------------------|
| AC-1.1 | **Given** выбран узел без `calendarUid`, **When** пользователь указывает дату, время начала и окончания и нажимает «Отправить в календарь», **Then** в Яндекс Календаре (список задач) появляется задача с `SUMMARY` = имя узла и `DESCRIPTION` = описание узла (или пусто). |
| AC-1.2 | **Given** успешный ответ CalDAV, **When** операция завершена, **Then** у узла заполнены `calendarUid`, `calendarStartAt`, `calendarEndAt`, `deadline` = дата начала, и в карточке виден признак «В календаре». |
| AC-1.3 | **Given** узел уже с `calendarUid`, **When** пользователь смотрит карточку, **Then** отправка недоступна (кнопка disabled или эквивалент) без создания дубликата. |
| AC-1.4 | **Given** конец диапазона раньше начала (или равен началу), **When** отправка, **Then** запрос не уходит, показывается ошибка валидации. |
| AC-1.5 | **Given** CalDAV вернул ошибку / нет сети, **When** отправка, **Then** узел остаётся без привязки, признак не показывается, пользователь видит сообщение об ошибке. |

### AC-2. Признак привязки

| ID | Given / When / Then |
|----|---------------------|
| AC-2.1 | **Given** узел с `calendarUid`, **When** открыта карточка, **Then** признак «в календаре» отображается. |
| AC-2.2 | **Given** узел без `calendarUid`, **When** открыта карточка, **Then** признака нет. |

### AC-3. Глобальная синхронизация

| ID | Given / When / Then |
|----|---------------------|
| AC-3.1 | **Given** в шапке рядом с индикатором сохранения есть кнопка sync, **When** на карте есть ≥1 привязанный узел и пользователь нажимает sync, **Then** приложение запрашивает актуальные данные задач из CalDAV. |
| AC-3.2 | **Given** в календаре у задачи изменены дата/время, **When** sync успешен, **Then** у соответствующего узла обновлены `calendarStartAt` / `calendarEndAt` и `deadline` (дата начала). |
| AC-3.3 | **Given** задача в календаре со статусом выполненной и известным временем завершения, **When** sync, **Then** `status` узла = `Done` и в конец `description` добавлена строка `Выполнена в календаре дд.мм.гггг чч:мм` с этим временем (формат дня.месяца.года и часов:минут). |
| AC-3.4 | **Given** задача выполнена, но времени завершения в календаре нет, **When** sync, **Then** в пометке используется дата/время момента sync. |
| AC-3.5 | **Given** в описании уже есть строка, начинающаяся с `Выполнена в календаре`, **When** повторный sync при всё ещё выполненной задаче, **Then** вторая такая же пометка не добавляется. |
| AC-3.6 | **Given** существующее описание узла непустое, **When** добавляется пометка о выполнении, **Then** исходный текст описания сохраняется (пометка только дополняет). |
| AC-3.7 | **Given** добавление пометки превысило бы 2000 символов, **When** sync, **Then** основной текст не затирается; пометка не добавляется «тихо»; по узлу фиксируется ошибка/предупреждение в результате sync. |
| AC-3.8 | **Given** нет привязанных узлов, **When** sync, **Then** операция завершается без ошибки (no-op) с понятным результатом. |
| AC-3.9 | **Given** часть узлов синхронизировалась, часть нет, **When** sync завершён, **Then** успешные узлы обновлены, по неуспешным видно ошибку; общий статус операции отражает частичный успех. |

### AC-4. Данные и сохранение

| ID | Given / When / Then |
|----|---------------------|
| AC-4.1 | **Given** create или sync изменили узлы, **When** операция успешна, **Then** изменения попадают в дерево и сохраняются в `data/mindmap.json` через существующий механизм сохранения. |
| AC-4.2 | **Given** карта без календарных полей (старый JSON), **When** приложение загружает данные, **Then** узлы работают как раньше, без падения. |
| AC-4.3 | **Given** секреты CalDAV, **When** проверка репозитория, **Then** токен/пароль отсутствуют в git (только `.env.local` / env). |

### AC-5. UI / UX минимальный

| ID | Given / When / Then |
|----|---------------------|
| AC-5.1 | **Given** выбран узел, **When** пользователь смотрит правую панель, **Then** доступны контролы даты, диапазона времени и отправки (если не привязан). |
| AC-5.2 | **Given** узел привязан, **When** пользователь смотрит карточку, **Then** видны сохранённые дата/время начала и окончания из календарных полей. |
| AC-5.3 | **Given** пользователь на любой вкладке (Outline/Карта), **When** смотрит шапку, **Then** кнопка sync доступна рядом с индикатором сохранения. |

---

## 8. Вне скоупа v1

- Создание VEVENT / встреч с Телемостом  
- Push изменений имени/описания/статуса из приложения в календарь  
- Кнопки create/sync на outline и на карте  
- Несколько задач на один узел  
- Выбор чужого календаря / нескольких аккаунтов  
- Авто-sync по таймеру / webhook  

---

## 9. Проверочный сценарий (smoke)

1. Открыть узел без календаря → указать завтра 09:00–10:00 → Отправить.  
2. В [calendar.360.yandex.ru](https://calendar.360.yandex.ru/) в задачах появилась запись с именем узла; в карточке — признак.  
3. В календаре перенести задачу на другой день/время → Sync в шапке → на узле новые дата/время.  
4. Отметить задачу выполненной в календаре → Sync → статус Done + строка в описании.  
5. Sync ещё раз → вторая строка «Выполнена…» не появляется.
