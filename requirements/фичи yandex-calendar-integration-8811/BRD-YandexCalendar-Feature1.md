# BRD — Интеграция с Яндекс Календарём (Фича #1)

**Ветка:** `cursor/yandex-calendar-integration-8811`  
**Версия:** 0.1 (черновик)  
**Дата:** 06.07.2026  
**Статус:** обсуждение, реализация не начата

---

## 1. Контекст (как есть сейчас)

Узел (`MindNode`) хранит:

| Поле | Сейчас |
|------|--------|
| `deadline` | только дата `YYYY-MM-DD`, **редактируется** в NodeCard |
| `status` | `New` / `Done` / `Cancelled` / `null`, **редактируется** в NodeCard |
| время суток | **нет** |

Создание событий в Яндекс Календаре — через **CalDAV** (пароль приложения), публичного REST API для событий нет. Типичный путь: `https://caldav.yandex.ru/calendars/{email}/events-default/{uid}.ics`.

Outline показывает дату в строке узла; на карте — нет. Контекстных меню нет, действия — через выбор узла и NodeCard.

---

## 2. Цель фичи #1

Из **outline** и **карты** по узлу создавать задачу в Яндекс Календаре с указанием даты и времени. Дата и время в приложении после привязки только отображаются (не редактируются). При изменении в календаре — обновление в приложении (допустима ручная синхронизация по кнопке). При отметке «выполнено» в календаре — статус узла `Done`.

---

## 3. Черновик функциональных требований

### FR-1. Создание задачи в календаре из узла

- Из **outline** и **карты** для выбранного узла доступно действие «Создать в Яндекс Календаре».
- Перед созданием пользователь указывает **дату и время** (и, вероятно, длительность — см. раздел 4).
- В календаре создаётся объект, связанный с узлом (нужен внешний идентификатор, например CalDAV `UID` + URL календаря).
- В календарь передаётся минимум: **название** (`name`), опционально **описание**, **ответственный** (если решим).

### FR-2. Отображение даты/времени в приложении

- После привязки к календарю у узла показывается **дата и время** (не только дата).
- Поле **read-only** в приложении: менять можно только в календаре.
- Отображение — в NodeCard; в outline — в badges (сейчас там только `deadline`); на карте — **нужно решить** (сейчас даты нет).

### FR-3. Синхронизация даты/времени из календаря

- При изменении даты/времени в календаре приложение должно отражать актуальные значения.
- Допустима **ручная синхронизация** (кнопка «Синхронизировать» — на узел или глобально).
- Источник истины для даты/времени после привязки — **календарь**.

### FR-4. Синхронизация статуса «выполнено»

- Если в календаре задача/событие отмечено выполненным → в приложении `status = Done`.
- Обратное направление (Done в приложении → календарь) в описании **не задано** — нужно уточнить.

### FR-5. Модель данных

- Новые поля узла (примерно):
  - `calendarEventId` / `calendarUid` — связь с событием;
  - `scheduledAt` — ISO datetime (дата + время);
  - `calendarSyncedAt` — время последней синхронизации;
  - возможно `calendarLink` — ссылка на событие в веб-интерфейсе.
- Связь **1 узел : 0..1 событие** (по умолчанию; иначе — отдельное решение).

### FR-6. Аутентификация

- Подключение к Яндекс Календарю (CalDAV): логин + пароль приложения или OAuth — **нужно выбрать**.
- Учётные данные не в `mindmap.json` (секреты на сервере / env).

### FR-7. API

- Серверные маршруты, например:
  - `POST /api/calendar/events` — создать из узла;
  - `POST /api/calendar/sync` — синхронизация (узел или всё дерево).
- Клиент после операций обновляет локальное дерево и сохраняет через существующий `POST /api/nodes`.

## 4. Нефункциональные требования (черновик)

- Синхронизация требует сети (противоречит BRD v1.0 «работает без интернета» — см. раздел 5).
- Один пользователь / один календарь — разумное допущение для v1.
- Часовой пояс: явно фиксировать (например, `Europe/Moscow`).

## 5. Логические нестыковки и открытые вопросы

### 5.1. `deadline` vs дата/время календаря — главный конфликт

Сейчас есть редактируемое поле «Срок выполнения» (`deadline`, только дата). Требование — read-only дата+время из календаря.

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| A. Заменить `deadline` на `scheduledAt` после привязки | Одно поле | Ломает узлы без календаря; теряется «мягкий дедлайн без времени» |
| B. Два поля: `deadline` (локальный) + `scheduledAt` (из календаря) | Гибкость | Две даты на экране — путаница |
| C. `deadline` скрывается/блокируется после привязки | Простая модель | Нужна миграция и правила для старых узлов |

**Нужно решение:** одно поле или два? Что с узлами, у которых уже заполнен `deadline`, но нет события в календаре?

---

### 5.2. VEVENT vs VTODO — «задача» или «событие»?

- В Яндекс CalDAV часто используют коллекцию `events-default` → по сути **VEVENT** (встреча во времени).
- «Выполнено» для **VEVENT** в iCal нестандартно; у **VTODO** есть `STATUS: COMPLETED`.
- В UI Яндекса «отметить выполненным» может вести себя иначе для событий и задач.

**Вопрос:** создаём **событие с временем** или **задачу (VTODO)**? От этого зависит FR-4 и реализуемость «выполнено» через CalDAV.

---

### 5.3. Двунаправленная синхронизация статуса

Задано только: календарь → приложение (`Done`).

Не задано:

| Сценарий | Поведение? |
|----------|------------|
| Пользователь ставит `Done` в NodeCard | Обновлять календарь? |
| Пользователь ставит `Cancelled` в приложении | Что в календаре? |
| В календаре отменили / удалили событие | `Cancelled`? `null`? ошибка синхронизации? |
| В приложении сняли `Done` | Разрешено? Что в календаре? |

Без правил — конфликты при ручной синхронизации.

---

### 5.4. Read-only дата/время vs редактируемый `deadline`

Пока узел **не** привязан к календарю, `deadline` остаётся редактируемым?

При создании события: подставляем дату из `deadline` (время — дефолт, напр. 10:00) или всегда отдельный диалог?

---

### 5.5. Точка входа «из outline и из карты»

Контекстных меню нет. Варианты:

- кнопка в NodeCard (общая для обоих видов);
- отдельная кнопка/иконка в строке outline и на узле карты;
- контекстное меню (новый паттерн).

**Вопрос:** достаточно NodeCard + выбор узла в любом виде, или нужны действия прямо на узле без правой панели?

---

### 5.6. Карта не показывает дату

BRD для карты: статус и ответственный, без срока. Если дата/время — ключевой атрибут календарной задачи, на карте её не видно.

**Нужно ли** показывать `scheduledAt` на `MapNode`?

---

### 5.7. Длительность и тип события

Указаны дата и время начала. Не указаны:

- длительность (30 мин / 1 ч / весь день);
- целодневное событие;
- повторение (RRULE).

Без длительности CalDAV/ICS неоднозначен.

---

### 5.8. Удаление и «осиротевшие» связи

| Событие | Узел |
|---------|------|
| Удалено в календаре | Очистить связь? Оставить последние дату/статус? |
| Удалён узел в приложении | Удалять событие в календаре? |
| Повторное «Создать в календаре» | Ошибка или новое событие? |

---

### 5.9. Синхронизация прочих полей

Не описано:

- переименование узла → заголовок в календаре;
- описание / ответственный;
- только дата/время и статус Done.

Иначе рассинхрон названий неизбежен.

---

### 5.10. Противоречие с NFR из BRD v1.0

Текущий BRD: локально, без интернета, один JSON, без секретов.

Интеграция требует сеть, учётные данные, серверные вызовы CalDAV. Нужно **явно расширить** NFR: «офлайн-режим без календаря; синхронизация — по запросу при наличии сети».

---

### 5.11. Часовой пояс

`deadline` — дата без TZ. CalDAV — `DTSTART`/`DUE` с TZID или UTC.

**Вопрос:** всегда `Europe/Moscow` или TZ браузера/пользователя? Летнее время?

---

### 5.12. Объём ручной синхронизации

- Кнопка на **одном узле** или **«Синхронизировать всё»**?
- При 500 узлах и 50 привязках — N запросов к CalDAV; нужны лимиты и индикация ошибок по узлам.

---

### 5.13. Статус `Cancelled` vs «выполнено» в календаре

В приложении три статуса; в календаре отмена ≠ выполнение.

Нужна таблица соответствий:

| Календарь | Приложение |
|-----------|------------|
| COMPLETED / выполнено | `Done` |
| CANCELLED / удалено | `Cancelled`? |
| перенесено | только дата/время |

---

### 5.14. Узел без статуса (`null`)

Сейчас статус может быть пустым. После создания в календаре: автоматически `New` или оставить `null` до первой синхронизации?

---

### 5.15. Многопользовательский сценарий (даже в перспективе)

Один `mindmap.json`, один набор CalDAV-учёток на инстанс. Если разные люди работают с одной картой — чей календарь? Поле `responsible` не привязано к аккаунту Яндекса.

---

## 6. Сводка: что решить до плана реализации

1. **Модель даты:** `deadline` vs `scheduledAt`, одно или два поля.
2. **Тип в CalDAV:** VEVENT или VTODO (критично для «выполнено»).
3. **Направление синхронизации статуса:** только календарь → app или двусторонняя.
4. **Поведение при удалении** события или узла.
5. **UI:** где кнопки создания/синхронизации; показывать ли время на карте.
6. **Длительность** и целодневные события при создании.
7. **Синхронизация name/description** или только дата + Done.
8. **Аутентификация:** пароль приложения (проще) vs OAuth.
9. **Часовой пояс** по умолчанию.
10. **Обновление BRD/NFR** под зависимость от сети.
